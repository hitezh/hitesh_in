Within four days in May, GitHub and Anthropic both shipped coding agents that take a description of work and come back with code. With GitHub's new [Copilot coding agent](https://github.blog/news-insights/product-news/github-copilot-meet-the-new-coding-agent/), you "assign one or more GitHub issues to Copilot" and it comes back with a pull request. Three days later Anthropic made [Claude Code generally available](https://www.anthropic.com/news/claude-4). In both cases the input is a written statement of what you want, and the output is a change somebody still has to approve.

That is what I mean by intent-driven development: you state the intent, and the tool writes the code. Andrej Karpathy gave the casual version a name in February, ["vibe coding"](https://x.com/karpathy/status/1886192184808149383), where you "forget that the code even exists." Fine for a weekend project. For a team shipping software that customers pay for, I think the shift has a duller consequence, and it is the one to plan around.

## When intent is the input, precision is the scarce skill

If the machine writes the code from what you tell it, then what you tell it puts a ceiling on what you get back. A vague ticket used to be cheap, because the engineer who picked it up would walk over, ask three questions, and fill the gaps from what they knew about the product. An agent fills the gaps too. It just fills them with guesses, confidently and at speed.

So the skill that gets scarce is writing down what you actually want: the behavior, the edge cases, what must not change, and how you will know it worked. Most teams are weak at this, because their tickets were written as reminders for a colleague who already had the context.

## The other half is checking the result

Intent gets you a draft. Someone still has to decide whether the change does what was meant, and the tools are built on that assumption. GitHub's agent won't run your Actions workflows "without your approval," and the developer who asked for the pull request can't be the one who approves it. Google already works this way at scale. In October, Sundar Pichai said that ["more than a quarter of all new code at Google is generated by AI, then reviewed and accepted by engineers."](https://blog.google/inside-google/message-ceo/alphabet-earnings-q3-2024/) The generation gets the headline, but the reviewing and accepting is where the responsibility sits.

There is early data on what happens when teams lean on the generation and neglect the rest. Google's [2024 DORA report](https://cloud.google.com/blog/products/devops-sre/announcing-the-2024-dora-report) found that as AI adoption rose, delivery stability fell by an estimated 7.2% and throughput by 1.5%. The authors' reading is that a better development process doesn't automatically improve delivery "without proper adherence to the basics of successful software delivery, like small batch sizes and robust testing mechanisms." It is a correlation from a survey and can't prove cause. Still, producing code got easier, and knowing it is right did not.

## The objection: models will get good enough to guess

The strongest objection is that a good enough model will work out what you meant from a sloppy request. A better model does make fewer mistakes per line. It still can't know a business rule nobody wrote down, or why that odd edge case exists for one large customer. Ambiguity lives in the request, and a model handed an ambiguous request picks an answer. The faster the tool, the more of those picked answers reach your codebase before anyone notices.

## Where I would put the money

If I ran an engineering team today, more AI seats would not be my first spend. I would invest in what makes intent usable:

1. Rewrite your issue template so every ticket carries acceptance criteria and a couple of concrete examples. If a new hire couldn't build the right thing from the ticket alone, an agent can't either.
2. Treat tests as the spec in a form a machine can check. Ask for the test that fails before the change and passes after it, and look at that before the code.
3. Keep changes small, as DORA recommends. A giant pull request is hard to review properly whoever wrote it.
4. Protect your senior engineers' review time and count it as real work, because that is where correctness now gets decided.
5. Track reverts and post-merge incidents next to how much ships. If both climb together, you have bought speed with stability.

My bet is that the teams who get the most out of these tools will be the ones that were already good at saying exactly what they wanted. Pick ten tickets from your current backlog: how many could an agent build correctly without a conversation first?
